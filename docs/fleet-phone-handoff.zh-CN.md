# Fleet 与手机工位：协作缺口交接

## 需要调查的问题

一次真实使用中，用户要求一个 API 入口的 Agent 查看手机 `phone use` 工位并说明问题。它用 Fleet 列出了工位，随后通过 SSH 读取 tmux 和会话，而没有通过 Fleet 联系目标 Agent。用户指出，这条协作路径没有达到他对 Fleet 的预期。

这既是需要调查的产品问题，也包含发起 Agent 自身的选择：**本次没有实际调用 `fleet send`，不能声称已经复现消息发送失败。**

## 已观察事实

- Fleet `list` 能发现手机工位和状态；目标当时显示 `idle`。补查目标收件箱为空，但没有发送新的诊断请求。
- 原型的发送接口要求提供 `HOST/SERVER/%PANE` 形式的回复地址；API 会话没有天然对应的 tmux pane。非 pane 调用方如何收取回复需要实验，不能冒用现有工位身份。
- 目标 Agent 目前需要主动查询收件箱。已有手动提示后的双向收发样例，不证明自动发现、自动启动处理或最终结果回收。
- 观察 pane 现场时本次使用了 tmux/SSH；是否应增加 Fleet 入口，还是把这些能力保留给原生命令，是设计选择。
- 被观察的手机 Agent 在一个用户已明确请求的发送任务上再次询问许可，并从一次被杀的 `uiautomator` 和一次空的包名过滤窗口树推断读屏完全不可用；这属于 Agent 决策和手机控制证据问题，不应混同为 Fleet 传输故障。
- 2026-11-01 发布前测试：Mac 上现有 5 项单元测试通过且进程正常退出；Android 16 的 Termux 环境中同样报告 5 项 `OK`，但测试进程退出时出现过 `Segmentation fault`（退出码 139）。用 ADB 配置 Termux PATH 和 `libtermux-exec-ld-preload.so` 时，单独运行部分测试也能复现；通过 SSH 时曾在测试报告 `OK` 后返回 255。尚未确定是 Python、Termux 执行兼容层、测试清理还是 SSH 等哪一层导致，**不能将手机测试记为完整通过，也不能据此断言 Fleet 业务逻辑出错**。

## 请接手者先做的事

1. 从仓库的 [`packages/fleet/`](../packages/fleet/) 检查 CLI 原型及其测试。手机 `phone-agent` 的实现与设备依赖尚未纳入本仓库；如果接手环境没有这些代码，先取得用户授权的工作区或代码版本，不要凭文档声称已经复现。
2. 分别从 tmux 工位和非 tmux API/CLI 入口发起同一个无副作用的问题，记录目标如何发现请求、如何确定返回地址、是否实际收到回复，以及哪些步骤需要人介入。
3. 单独观察目标已有任务、输入框草稿、多个请求、进程退出和网络中断。不要把写入成功、状态灯变化或 Agent 的一句“完成”视为现实任务成功。
4. 对照现有 Pi/harness 的能力与已有 tmux/SSH 工具，提出最小可选改进。记录否定方案和真实阻碍，不预设新服务、消息代理、固定工位角色或一套重协议。
5. 在隔离的 tmux server 中定位 Android 测试进程退出异常；核对测试断言、进程退出码、Termux 兼容层和 SSH 连接状态，避免触碰用户现有工位。

## 可衡量的验收

- **正向**：非 tmux 发起方请求手机工位执行可验证的只读任务；手机主动发现、完成并回传同一请求的结果，发起方核对证据。
- **反向**：手机工位向 Mac 工位发起一个可验证任务并收到结果。
- **安全的并发体验**：目标忙碌或存在用户草稿时，不破坏输入；离线、超时、重复发送、重启和取消都明确报告实际状态。
- **上下文与成本**：比较任务摘要与完整历史两种模式在真实任务中的可完成性、token 与时延，而非假设固定收益。

先复现并讨论，再决定是否修改 Fleet；保留 Agent 对底层工具与协作方式的选择权。相关背景见[对等工位设计](fleet-coordination.zh-CN.md)和[手机控制层](phone-agent.zh-CN.md)。
