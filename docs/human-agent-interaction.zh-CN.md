# 人机输入与反馈实验

## 目标与状态

用户希望在多个自主 Agent 协作时，能通过语音提供目标和解释，通过耳机听到简短反馈，并探索点头、摇头或轻触来回答当前问题。这是待验证的人机交互方向，不是 Fleet 已实现的功能，也不要求人类为每条 Agent 间消息充当中转。

把“人的输入不够快”拆成可观察的问题：问题是否值得打断人、是否明确当前在回答谁、是否能用一句话补充高信息量约束、Agent 是否能在等待期间继续工作，以及结果是否有需要时可追溯的证据。

## 硬件与输入路径

- DJI Mic Mini 可作为语音输入，耳机负责播放；接收器或蓝牙组合是否在具体手机、操作系统及 App 内正确路由，需要实机测试。现有音频桥或 Voice 客户端的局部成功不代表任意麦克风与输出组合均可用。
- 双击、三击、媒体按键、点头和摇头是不同输入方式；耳机支持某个内建手势，不代表第三方程序可读取原始传感器或接收任意自定义事件。
- Android 的头部追踪协议依赖手机厂商和耳机支持；Android API 说明头部追踪传感器通常不对普通 App 可用。选择硬件前先对目标平台验证可读取性，而不是仅依据“空间音频”营销名称。[Android 头部追踪协议](https://source.android.com/docs/core/interaction/sensors/head-tracker-hid-protocol)、[Android Sensor API](https://developer.android.com/reference/android/hardware/Sensor#TYPE_HEAD_TRACKER)
- 一条可尝试的 Mac 路径是第三方开源 [Sony Head Tracker](https://github.com/NicholasSlattery/sony-head-tracker)：项目文档报告特定设备的 macOS 实机结果，其他型号和目标手机仍须分别验证。该路径不是本项目依赖或兼容性承诺。

## 交互假设

语音适合表达较丰富的目标、背景、纠正与约束；动作适合回答刚提出且范围明确的简单问题，或表达打断、暂停、继续。头部动作应仅在用户知道当前问题和接收方的窗口内解释；走路、吃东西、转头和设备重连是必须测量的误触情形。

多个 Agent 同时提问时，探索如何让人知道当前听到的是谁、回答会发给谁、是否还有别的待处理事项。不要将一个模糊的动作自动解释为对所有待处理操作的许可。人可以忽略、延后、补充或纠正；输入接口应保留这些可能性。

## 小规模验收

1. 用现有麦克风和耳机完成一条真实的“说出只读任务 → Agent 执行 → 人听到实际结果”链路，记录每段耗时与音频来源；先不用新硬件。
2. 测试设备的触摸/媒体按键能否可靠交给自建程序，观察其与当前播放、通话和系统助手的冲突。
3. 如能借到支持可读头动数据的耳机，先只记录点头、摇头和日常动作的误识别率与延迟；确认可用后再将事件关联到一个具体问题。
4. 再测试多个 Agent 同时需要反馈、用户中途打断和离线后恢复。记录成功率、误触、听觉负担及需要人工协调的次数。

语音任务总线和 Fleet 通信都是现有实验；避免把音频路由活动、消息存入、Agent 结束或设备产生动作事件，误写为人实际听到、理解或授权的证明。
