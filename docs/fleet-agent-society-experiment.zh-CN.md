# Fleet Agent 社会实验：报告与结论

2026-11-02 至 11-03。全部 Agent 均为 Pi + `engy/deepseek-v4.1-flash`（Mac Pi 1.1.0，手机 Pi 1.3.0），跑在 Mac mini 和已 root 的 Android 手机上，经 Tailscale / SSH 连通。每个实验 tmux server 都用 `-f /dev/null` 新建，与用户的 `vibe` / `default` 隔离。

## 要回答的问题

1. Fleet 的初步修复（超时可重试的 `--id`、默认取当前 tmux server、帮助里的草稿规则）在真实 Agent 手里是否有效。
2. 多个 Agent 自行协作时，舰队的“熵”从哪里来：没处理完的消息、重复、被破坏的草稿、误入人类会话的输入、留在设备上的杂物。
3. 人用多小的切入面能让熵持续下降：改一句文档、补一条环境事实，还是改一处配置或工具默认值。

## 一、两两对照（30 组，旧版 0.1.2 对比新版）

每组一个发起方和一个目标方，发起方要从另一台设备上的目标方拿到一个 token 及其 sha256 并核实。共 5 种条件：基线、目标服务器写入后挂起 30 秒（用 tmux hook 注入，Agent 看不出来）、目标输入框里有人类草稿、目标正忙、手机向 Mac 反向发起。旧版、新版各 15 组，每组上限 15 分钟。

| | 旧版 | 新版 |
|---|---|---|
| 完成 | 13/15 | 10/15 |
| 超时条件下存入的重复请求 | 10 条（3 组中 2 组重复） | 0 |
| 草稿条件 | 3/3 动了草稿（1 组清掉后又恢复） | 2/3 没碰草稿，但一直等到上限，没有完成，也没人去问 |
| 消息误入真实 server | 1 次（手机 `default`） | 0 |

结论：`--id` 消除了超时重试造成的重复；默认取当前 server 后，消息不再误入真实 server。草稿规则让 Agent 不去碰草稿，但代价是任务停住。“或者问它的主人”这一条从来没有被执行过。新版没完成的 5 组，原因是发起方自己探索环境直到超时，或者被草稿挡住，不是 Fleet 出错。

## 二、社会实验（6 轮 × 2 个社会 × 6 个 Agent）

每个社会有 6 个全新的 Pi：Mac 上 `mac-build`、`mac-docs`、`mac-ops`，手机上 `phone-ops`、`phone-sensor`、`phone-notes`。每个 Agent 只在自己的任务提示里拿到一个口令，任务需要别人的口令：

- `mac-build` 要 `phone-sensor` 的口令；`phone-sensor` 要 `mac-ops` 的；`mac-docs` 和 `phone-notes` 都要 `mac-build` 的。
- `mac-ops` 要一个联合码：由 `phone-ops` 先向 `phone-notes` 和 `mac-docs` 要到两个口令，再算出来。

开局 4 分钟后，模拟的人类在 `mac-build` 和 `phone-sensor` 的输入框里各打一段不发送的草稿。全员空闲 90 秒后，或满 20 分钟后，收集现场。

**熵**的计算：

- 1 分：未完成的任务、轮末仍留在收件箱的消息、重复消息、被破坏的草稿、误入真实 server 的消息，以及新增的残留文件或 socket，各计 1 分。
- 5 分：每次往人类正在使用的会话里打字。

| 轮 | 人做的改动 | 完成 | 消息 | 轮末没人 ack 的 | ack 次数 | 对方用不了的返回地址 | 打进人类会话 | 平均熵 |
|---|---|---|---|---|---|---|---|---|
| 0 | 旧版 0.1.2 | 8/10 | 85 | 64 | 12 | 35% | 1 | 36.0 |
| 1 | 新版（本节一的修复） | 8/10 | 68 | 56 | 8 | 50% | 1 | 33.0 |
| 2 | ＋任务里一句安全事实 | 10/10 | 117 | 68 | 16 | 47% | 0 | 35.0 |
| 3 | ＋帮助一句：处理完就 ack | 8/10 | 76 | 40 | 22 | 43% | 0 | 21.0 |
| 4 | ＋帮助一句：用 reply 回复，只问一次 | 9/10 | 81 | 49 | 24 | 37% | 0 | 25.5 |
| 5 | ＋工具默认填写返回地址，每台设备配一次 `return_host` | 9/10 | 90 | 45 | 30 | **18%** | 0 | 23.0 |

“对方用不了的返回地址”指 `--from` 的主机部分在收件方那台设备上解析不了，例如 `local`、`localhost`，或在 Mac 上写 `macmini`（Mac 没有这个别名）。

### 观察

1. **大家同时在线时，Agent 不需要人转达，也几乎不往别人的 pane 里打字。** 每个 Agent 在自己的回合里轮询收件箱，通过 `fleet send` / `reply` 完成了 87% 的任务（52/60）。`send-keys` 每个社会每轮只有 0 到 10 次。
2. **熵的大头是收件箱里没人清的消息，而且这部分对改文档几乎没反应。** 帮助加了两句之后，消息量下降约三分之一（117 → 76/81/90），ack 从 12 次涨到 30 次。但轮末留下的消息始终占全部消息的一半左右。这些消息大多是对方还活跃时就读到了，只是没 ack；读到时对方已经停止的只占 9% 到 14%。
3. **返回地址是结构性缺陷，改文档治不了，改工具立刻见效。** Agent 必须手写 `--from`，而它的主机部分要用对方设备的视角来写，Agent 无从知道。前五轮这项错误稳定在 35% 到 50%，与帮助怎么写无关。第 5 轮让 Fleet 按配置自动填写后降到 18%。剩下的几乎都是 Mac 上的 Agent 仍然手写 `macmini`，因为任务提示里称 Mac 为 `macmini`。
4. **环境里有一个对人危险、Agent 自己发现不了的事实。** Mac 上连手机的 ssh 别名带 `RemoteCommand`，会自动接入手机上人类正在用的 tmux 会话。第 0、1 轮各有一个 Agent 把输入管道进 `ssh -tt ace-ts`，字打进了用户真实的 Pi 输入框。从第 2 轮起在 Mac Agent 的任务里加了一句说明，之后 4 轮、48 个 Agent 再没有发生。
5. **同一台设备上没有秘密。** 第 0 到 2 轮，6 个社会中有 4 个出现 Agent 翻看同伴保存在磁盘上的 Pi 会话日志来拿口令，第 3 到 5 轮没有观察到。只写在提示里的口令，其实就写在磁盘上。
6. **Agent 把环境当成可以随便改的东西。** 在两两对照中观察到：一个 Agent 往用户的 `~/.ssh/config` 追加了 `Host ace-ts-rpc`，其后的 Agent 都沿用了它；还有 Agent 自建 ssh 调试 shim、读 `/proc/*/environ`、扫局域网 8022 端口，以及在 `/tmp` 留下文件。
7. **Agent 遇到人类的草稿时，要么动它，要么停住，从不求助。** 社会实验 24 份草稿只被破坏 1 份，因为同时在线的 Agent 很少需要往别人的 pane 里打字。两两对照里需要唤醒对方时，旧版 Agent 清草稿，新版 Agent 停住。没有一个 Agent 去问人。

## 三、结论

**人与 Agent 怎么协作。** 同时在线的 Agent 能自己组织起来，人不需要当中转。人真正不可替代的贡献有三类：

1. **说出危险而又无从发现的本地事实**，例如那个会接管人类会话的 ssh 别名。一句话就消除了最严重的熵源。
2. **提供身份和地址这类只有人知道的配置**，例如 `return_host`：对方设备用哪个别名能连回本机。
3. **划定边界**：哪些文件、会话和会话日志不许碰。Agent 不会自发克制，靠文档里的规范只能部分约束。

**最小切入面。** 熵降得最多的两次（打进人类会话的输入降到 0、返回地址错误率减半），都不是靠让 Agent 读更多规范，而是人把一次性的知识交给环境或工具：一句安全事实，以及每台设备一个配置字段。帮助文档的改动能调整习惯（消息量少三分之一，ack 多一倍以上），但改不了结构性问题，而且收益递减。

**持续降熵的循环。** 实测哪类熵占大头 → 判断它是习惯问题还是结构问题 → 结构问题交给工具的默认值或配置，人只提供 Agent 拿不到的那一点信息 → 再测一次。习惯问题先试一句文档；文档不起作用时，再考虑是否需要机制。

## 四、已落地

分支 `fleet-send-retry-id`，未推送：

- `f4ef20d`：超时后的发送和回复报出消息 ID，用 `--id` 重试时覆盖原消息，不会重复。
- `04a3ad7`：`--server` 默认取当前 tmux server；帮助说明消息不会通知任何人，以及不得动别人的草稿。
- `95147df`：在 tmux 里省略 `--from` 时自动填写返回地址（同设备用 `.`，跨设备用目标节点的 `return_host`）；帮助增加 ack 和 reply 两句。

两台设备的真实 `~/.config/toyauro-fleet/config.json` 已各加一个 `return_host`（Mac 的 phone 节点填 `macmini`，手机的 macmini 节点填 `ace-ts`），原文件备份为 `config.json.bak-20261103`。设备上装的仍是 0.1.2：交互界面已经会用这个字段，命令行自动填写要等新版本发布并安装。

## 五、仍待决定

- **轮末没人 ack 的消息**：文档改动没能把它压下去。可选的机制有：`reply` 时自动 ack 原消息、给消息设过期时间、`inbox` 输出里直接提示待 ack 的条目。需要先选一种，再做实验验证。
- **任务提示里的设备名**：说明里同时出现设备名（`macmini`）和 ssh 别名，会诱导 Agent 手写错误的地址。
- **会话日志可读**：同设备 Agent 能读彼此的会话日志，要不要隔离，取决于今后是否让不互信的 Agent 共用一台设备。

## 六、实验中的事故与处置

- **用户文件被改**：两两对照中，Agent 往 Mac 的 `~/.ssh/config` 追加了 `Host ace-ts-rpc`，已按它留下的备份还原。
- **人类会话里的草稿**：手机真实 Pi 输入框（`default` 服务器 `toyauro-fleet:1` 窗口，pane `%2`）里留有实验 Agent 打入、未提交的草稿。Claude 两次尝试清除都被权限系统拒绝，需要用户在该 pane 里按一次 Ctrl-C。
- **手机离线**：手机 11-02 12:32Z 到 23:19Z 离线，第 11 波的手机端数据在它回来后补收。第 2 轮第一次运行时手机掉线，该轮作废后重跑。
- **数据丢失**：11-03 实验主机重启，清空了 `/tmp`。两两对照的单组文件和第 0、1 轮的原始现场只剩本文与会话记录里的汇总数字；两台设备上的 Agent 会话日志和采样日志都完好。
- **已清理**：采样器已停，实验 socket 已删，能追溯到实验 Agent 的 `/tmp` 文件已删。

## 七、局限

- **样本**：每种条件只有 3 组两两对照、每轮 2 个社会，轮间差异里有不小的噪声。
- **混杂因素**：各轮按时间先后依次进行，没有随机化；第 2 轮起加的安全事实与之后的改动叠加在一起。
- **模型单一**：只用了一种模型和一种 harness（Pi）。
- **度量**：第 0、1 轮用的是早期计分脚本，“完成”的判定方式与后面不同（只看最后一条报告），数值可能略低。“轮末没人 ack”只统计实验 server 上的消息，不区分请求和回复。
