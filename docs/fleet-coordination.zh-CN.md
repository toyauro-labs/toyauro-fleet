# 对等工位与通信设计

## 目标与原则

手机和 Mac 是各自独立的 Agent 运行环境，通过现有工具交换信息、请求协助和返回结果；手机不只是远程执行器，Mac 也不是必需的中央控制器。

一个 tmux pane 可以承载一个通用 Agent 工位，名称和职责可随任务变化。`phone use` 是可变的工作名称，不是必须永久存在的角色。名称、状态灯和 pane 边界也不是安全隔离边界。

方向是先使用现有 Shell、tmux、SSH、Git 和 Agent harness，观察真实协作中的障碍；只有重复出现且现有工具无法解决的问题，才考虑沉淀为可替换的薄工具。不要预先假定需要中心服务、数据库、消息代理或一套固定的分工契约。直接使用底层工具始终是可选路径。

## 已有实验原型：范围与边界

2026-10-29 的工作区中存在一个独立 Fleet CLI 原型，复用 tmux 命名 buffer 和 SSH，提供 `list`、`send`、`inbox`、`reply` 和 `ack`。它与 `tmux-agent-adon` 分工不同：前者用于消息，后者显示工位名称及 Agent 报告的状态。

当时的实测包括 Mac 和手机之间双向发起、读取和回复，手机 Pi 在**人工提示后**主动读取并确认消息；独立 tmux server 还测试过跨 window、跨 session 和错误 pane 的拒绝。可据此说人工触发的消息往返有样例，不能据此说 Agent 会自行接收新任务。

当时的边界：

- `stored: true` 仅表示写入了目标 tmux server 的 buffer，不等于接收方已读取、执行或完成。
- 接收 Agent 需主动查询收件箱；原型不自动唤醒 Agent 或注入输入框。
- 消息仅在 tmux server 存活期间保留；掉线、重启和重复发送有各自边界，不承诺持久化或去重。
- 地址由设备、tmux server 和 pane 组成；pane 编号随 server 生命周期变化，名称也可能重复或变更。
- 状态灯是进程或适配器的报告，不能单凭 `idle` 推断任务完成、输入框安全或接收方仍然存活。
- API 会话或一次性 CLI 没有天然的 tmux pane 回复地址；如何适配需要单独验证。

**仓库状态**：该 CLI 原型当时尚未纳入远端仓库。本文只记录已有观察，不随文档引入原型代码，也不承诺本文所述能力已被当前仓库发布。

## 按需交换上下文

一次请求应让对方能理解当前目标及必要约束，并提供实际可访问的代码、文件、commit 或证据引用；缺信息时允许 Agent 继续追问。不要自动复制整段对话，也不要把发送方本机路径当作对方必然可访问的资源。

上下文压缩、同步完整历史与按需读取各有成本；缓存、模型、重试和重复读文件都会改变结果。对 token、时延与质量应先测量，不预设固定节省比例。

## 待验证，而非既定实现

1. 目标空闲、忙碌、用户正在输入或有草稿时，如何让请求被发现而不覆盖现有工作。
2. 能否复用 Pi 等 harness 的已有消息和生命周期接口；其他 harness 各自的能力应分别验证，不假定共享同一协议。
3. 发送方如何识别已存入、已接收、已回复及失败/超时；最终结果如何与请求关联，避免把其他回合误当回复。
4. API 会话或一次性客户端的身份与回复方式；别名重复、pane 重建、目标离线以及重复请求如何表现。
5. 什么时候真实需要本地持久化、去重、离线投递或其他机制；这些均应由实验推动。

首个端到端实验：从一个工位向手机工位发送无副作用的真实任务，让目标无需人工提示便发现并处理，再把可核对结果返回给原发起方；反向重复。额外覆盖忙碌、草稿、并发、断线和重启。不能将“写入终端”或状态灯变化作为最终成功证据。
